StructPINN DeepONet helper note

Purpose

This benchmark shows the intended helper pattern for the summer physics-informed DeepONet project. The model can be any operator surrogate that emits a fixed-grid vector. StructPINN only needs that vector and a physically justified constraint object.

Generic pattern

raw = deeponet(params, input_parameters, output_grid)
constraint = constraint_from_grid_and_sample(output_grid, sample_metadata)
corrected = correct(constraint, raw)
loss = supervised_loss(corrected, target)

Recommended reusable pattern

Build correction contexts once per sample when the grid and sample metadata are known.

contexts = heat_correction_contexts(data, weights, mode = :full, cached = true)
loss = context_hard_loss(params, contexts, output_grid)

The synthetic heat helper supports these modes:

mode = :boundary_only
mode = :mass_only
mode = :box_only
mode = :boundary_box
mode = :full

Use :full for boundary, mass, and box correction together. Use the smaller modes for ablations and diagnostics.

Pure box correction can hit active-bound kinks. In that case the projection status is not success and no training gradient is claimed. In this helper, box-only correction is therefore used as an evaluation ablation unless the branch is known to be regular.

For a trained model, use the same contexts during evaluation.

corrected = context_projected_field(params, context, output_grid)

This avoids rebuilding the sparse constraint and its cached factorization inside every training step. It is the pattern to adapt once the summer DeepONet data structure is available.

Summer adapter pattern

For project data that is not shaped like the synthetic heat samples, build generic contexts from constraint rows and per-sample equality values.

rows = boundary_mass_rows(weights)
contexts = operator_correction_contexts(
    summer_samples,
    length(output_grid),
    equality_rows = rows,
    equality_values = sample -> [sample.left_bc, sample.right_bc, sample.balance],
    lower = lower_bound,
    upper = upper_bound,
    weights = weights,
    mode = :summer_adapter,
)

raw = summer_deeponet(params, sample, output_grid)
corrected = corrected_output(raw, contexts[i])

The equality rows can be replaced with any physically justified linear rows. The values can be constants or functions of each sample.

Exported batch adapter

When the summer code can export a CSV batch, use the file-backed adapter before changing the training loop.

julia --project=benchmarks/deeponet benchmarks/deeponet/export_summer_batch_fixture.jl
julia --project=benchmarks/deeponet benchmarks/deeponet/constraint_audit.jl path\to\batch.csv
julia --project=benchmarks/deeponet benchmarks/deeponet/summer_batch_review.jl path\to\batch.csv
julia --project=benchmarks/deeponet benchmarks/deeponet/summer_batch_eval.jl path\to\batch.csv

The batch adapter accepts these column names:

case_id
raw_output
target_output
grid
weights
left_bc
right_bc
balance or energy_balance
lower_bound
upper_bound

Vector cells may use comma, space, or pipe separators. If vector cells contain commas, quote the whole cell in the CSV. Scalar bounds are expanded to the output length.

The adapter chooses a starting mode from available metadata, writes summer_batch_eval.csv and summer_batch_eval.md, and reports statuses, correction norms, RMSE, boundary violation, balance violation, and box violation.

Use `export_summer_batch_fixture.jl` only as a smoke fixture when no real summer export exists. It is not a geothermal result.

Use `summer_batch_review.jl` before train-time correction. It checks grid ordering, target endpoint consistency, target balance consistency, target bounds, and whether units still need review.

For a batch that includes features and target_output, run the gated train-time workflow after evaluation-only correction is stable.

julia --project=benchmarks/deeponet benchmarks/deeponet/summer_batch_train.jl path\to\batch.csv
julia --project=benchmarks/deeponet benchmarks/deeponet/summer_training_decision.jl

This trains a vanilla DeepONet-style surrogate, corrects the held-out predictions at evaluation time, checks the projection success rate, and trains through cached correction contexts only if the status gate passes. The default gate requires at least 95 percent successful evaluation projections. Use STRUCTPINN_SUMMER_BATCH_STEPS and STRUCTPINN_SUMMER_BATCH_SUCCESS_THRESHOLD to change the smoke-run size or gate threshold.

Use `summer_training_decision.jl` after training. It decides whether the result is ready for real-loop integration or should wait for a real export, unit review, or a passing status gate.

Guarded expansion and sparse work

Use these commands to decide whether to spend more compute or engineering time.

julia --project=benchmarks/deeponet benchmarks/deeponet/expanded_seed_gate.jl
julia --project=benchmarks/deeponet benchmarks/deeponet/run_expanded_seed_jobs.jl
julia --project=benchmarks/deeponet benchmarks/deeponet/sparse_internal_work_decision.jl

The expanded runner only launches long seed jobs when the gate passes. Synthetic seed expansion is allowed once core artifacts and larger-output sparse profiling exist. It does not wait for the summer batch, and every run row carries a synthetic or real scope label. The separate summer_claims_allowed check stays closed until a real exported batch passes the training gate, so synthetic expansion never turns into a geothermal claim. The sparse-internals decision should stay `defer_solver_internal_work` unless projection is measured as the bottleneck on a real summer-sized output.

Useful constraints

Boundary values are usually safe when the PDE case study has fixed Dirichlet values and the output vector includes boundary grid points. They can be represented by affine rows selecting the boundary entries.

Box bounds are useful when the modeled variable has known physical or validity limits. For geothermal temperature fields, bounds should come from units, operating range, or the simulation design domain. They should not hide model error, so correction norms must be reported.

Integral balance is useful only when the discrete model has a justified balance law. The synthetic heat helper uses a mass-like integral because the generated target carries that value as sample metadata. For geothermal cases, use an energy or integral balance only if the numerical model supplies a meaningful target quantity.

Positivity is useful for variables such as density, concentration, or normalized quantities. It should not be imposed on a temperature variable unless the chosen units and normalization make it physically valid.

Recommended summer integration

Start with evaluation-time correction on a trained DeepONet. This gives a fast feasibility check without changing the training loop.

Then add train-time correction through correct when the constraint is regular and the output shape is stable.

For train-time correction, prefer prebuilt cached contexts when the same sample appears across epochs.

Always log projection status, correction norm, RMSE, boundary violation, bound violation, and any integral-balance violation.

Interpretation

Hard correction certifies selected constraints when status is success. It does not prove the raw model is good. A large correction norm means the raw model is far from the feasible set.

Soft-plus-hard training is often the better practical path. The soft term encourages raw outputs near the feasible set, while the hard correction gives exact feasibility for reported outputs.
